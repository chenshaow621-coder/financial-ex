# 金融法规原子化拆解与构建说明

更新时间：2026-04-28  
适用项目：金融法规抽取、业务分类、图谱构建、闭环召回与合规查验

## 1. 文档定位

本文档用于说明本项目中“金融法规原子化拆解与构建”的完整工作流。它不是通用 RAG 方案说明，而是当前代码、页面、数据产物和人工核查机制的项目级说明。

当前系统已经完成以下核心能力：

1. 将金融法规 docx 文档拆解为可执行的原子规则。
2. 将原子规则映射到业务分类体系和具体业务场景。
3. 将业务分类、场景和原子规则写入 Neo4j 图谱。
4. 基于业务问题执行闭环召回、逐轮推理和最终合规结论生成。
5. 在人工核查清单中支持典型样本抽检、模糊原子复核和人工通过复核率统计。
6. 在模型推理页支持多 query / 多问题并行召回与推理。

## 2. 总体目标

金融法规不是普通文本。系统目标不是把法规切成段落后做相似度搜索，而是把法规重构为可审计、可召回、可推理的规则网络。

完整链路如下：

```text
法规 docx
  -> 文档切块
  -> Phase1 宏观类型扫描
  -> Phase2 实体精准抽取
  -> Phase3 事件组装与原子拆解
  -> 原子知识表
  -> 业务分类映射
  -> 场景挂接与主体侧关系
  -> Neo4j 图谱
  -> 闭环召回
  -> 合规判断与人工复核
```

系统设计原则：

- 原子规则必须能支撑后续合规判断，而不是只保留原文片段。
- 每条原子尽量包含完整的 `who / when / where / what / how`。
- 条文中的例外、排除、条件、禁止、授权应拆成独立原子，并保留逻辑关系。
- 对模糊表达、缺参数表达、外部引用不明表达必须打上人工复核标签。
- 召回结果必须能解释“命中了哪些规则、还缺哪些规则、为什么要继续召回”。

## 3. 法律原子的定义

本项目中的法律原子（LegalAtom）是最小可执行规范命题。它不是自然段，也不是单纯的句子，而是后续系统能用于判断、召回和解释的结构化规则单元。

### 3.1 核心字段

| 字段 | 含义 | 当前实现口径 |
| --- | --- | --- |
| `atom_id` | 原子唯一编号 | 由 `generate_atom_id` 生成，形如 `YZ-PSM-OBL-00001` |
| `source_document` | 来源法规文件 | 来自原始 docx 文件名清洗结果 |
| `article_reference` | 条款锚点 | 若上游数据有条款编号则保留 |
| `rule_type` | 规则类型 | 8 类核心规则之一 |
| `relation_type` | 原子逻辑关系 | `DEFAULT` / `EXCEPTION` / `EXCLUSION` |
| `parent_atom_id` | 父原子 | 例外或排除原子指向一般规则原子 |
| `who` | 执行主体 | 对应 5W1H 中的主体 |
| `when` | 触发时机 | 对应条件、期间、时点 |
| `where` | 适用场景 | 对应业务环节、系统、柜面、流程节点 |
| `what` | 核心对象 | 对应票据、账户、材料、身份信息等对象 |
| `how` | 行为或规则动作 | 对应应当、不得、可以、核查、提交、保存等动作 |
| `content_original` | 原始依据文本 | 原子对应的原始法规片段 |
| `is_ambiguous` | 是否模糊 | 模型识别到模糊词、缺参数或外部引用不明时置为 true |
| `review_reason` | 复核原因 | `NONE` / `AMBIGUOUS_TEXT` / `MISSING_PARAM` |

### 3.2 原子编号规则

当前编号由 `src/schema.py` 中的 `generate_atom_id` 生成。

格式：

```text
YZ-{法规来源代码}-{规则类型前缀}-{五位序号}
```

来源代码当前包括：

| 来源关键词 | 来源代码 |
| --- | --- |
| 票据法 | `NIL` |
| 支付结算 | `PSM` |
| 反洗钱 | `AML` |
| 账户管理 | `BAM` |
| 商业银行 | `CBL` |
| 其他来源 | `GEN` |

示例：

```text
YZ-PSM-OBL-00025
YZ-NIL-PRO-00102
YZ-AML-RPT-00318
```

## 4. 规则类型体系

当前 Stage3 抽取提示词使用 8 类核心规则类型。

| 规则类型 | 中文含义 | 典型关键词 | 系统含义 |
| --- | --- | --- | --- |
| `OBL_MANDATORY` | 强制义务 | 应当、必须、须、应 | 必须执行的前置检查或办理动作 |
| `PRO_FORBIDDEN` | 禁止性规定 | 不得、禁止、不予、严禁 | 触发后直接阻断或风险提示 |
| `PER_AUTH` | 授权允许 | 可以、有权、允许 | 表示允许空间或可办理路径 |
| `EVT_TRIGGER` | 条件触发 | 当、若、发生时、符合条件时 | 表示规则被激活的条件 |
| `VAL_THRESHOLD` | 阈值约束 | 日内、金额、超过、不超过 | 表示期限、金额、比例、数量等边界 |
| `PRC_FLOW` | 程序流程 | 申请、提交、审核、核查、办理 | 表示业务步骤或审核动作 |
| `OBL_ONGOING` | 持续性义务 | 保存、持续、定期、监测 | 表示持续维护和留存要求 |
| `RPT_DISCLOSURE` | 报告披露 | 报告、报送、通知、披露 | 表示监管报送或信息披露 |

业务使用时，禁止类和例外类规则优先级更高；材料、流程、阈值类规则用于判断是否具备最小可执行颗粒度。

## 5. 三阶段抽取流水线

核心文件：

- `src/prompt.py`
- `src/main.py`
- `src/run_stage1_2_ner.py`
- `src/schema.py`

### 5.1 输入数据

主要输入目录：

- `data/raw/`
- `data/副本entity_table_unified_v3.xlsx`

法规原文以 docx 为主。页面可以通过上传文件或勾选已有文件参与抽取。

### 5.2 Stage1：宏观类型扫描

函数：

- `build_stage1_prompt`

目标：

- 不直接抽具体词。
- 先判断法规切块中出现哪些宏观类型。
- 降低后续抽取负担。

当前宏观类型包括：

- 法律主体（WHO）
- 核心事项（WHAT）
- 时间情境（WHEN）
- 空间情境（WHERE）
- 规则类型（RULES）
- 业务分类

输出形式：

```text
法律主体(WHO),核心事项(WHAT),规则类型(RULES)
```

### 5.3 Stage2：实体精准抽取

函数：

- `build_stage2_prompt`
- `build_entity_dictionary`

目标：

- 针对 Stage1 命中的类型逐类抽取实体。
- 使用动态字典提供已有规范词。
- 允许模型发现字典外的新实体。

输出形式为 JSON 数组：

```json
[
  {"entity_name": "持票人", "entity_type": "法律主体(WHO)"},
  {"entity_name": "银行汇票", "entity_type": "核心事项(WHAT)"}
]
```

### 5.4 Stage3：事件组装与逻辑裂变

函数：

- `build_stage3_ee_prompt`
- `extract_3stage_with_retry`
- `EventAssemblyResult`
- `LegalAtom`

目标：

- 将实体碎片和原文重新组装成法律原子。
- 对复合句、但书、除外、条件分句进行物理拆分。
- 输出符合 `LegalAtom` 结构的 JSON。

关键规则：

- 一般规则使用 `relation_type=DEFAULT`。
- “但是”“但”引出的例外规则使用 `relation_type=EXCEPTION`。
- “除外”引出的排除规则使用 `relation_type=EXCLUSION`。
- 例外或排除原子通过 `parent_atom_id` 指向对应的一般规则。
- 遇到模糊程度词、模糊时间词、缺少关键参数、外部引用不明时，必须设置 `is_ambiguous=true`。

### 5.5 输出产物

默认输出目录：

- `data/processed/`

常见产物：

| 文件 | 含义 |
| --- | --- |
| `phase1_entities_checkpoint.xlsx` | Phase1/2 实体抽取结果 |
| `legal_atoms_v4_final.xlsx` | 原子抽取结果 |
| `legal_atoms_evaluated_final.csv` | 评估后原子结果 |
| `legal_atoms_business_taxonomy.xlsx` | 业务分类后的原子结果 |

原子输出建议至少包含：

```text
atom_id, source_document, rule_type, relation_type, parent_atom_id,
who, how, when, what, where, content_original,
is_ambiguous, review_reason
```

## 6. 业务分类与图谱构建

核心文件：

- `src/business_taxonomy_pipeline.py`
- `src/business_taxonomy_app.py`
- `src/export_business_taxonomy_cypher.py`

### 6.1 业务分类体系

业务分类体系来自：

- `data/raw/业务分类体系.docx`

系统读取后解析出：

- 业务板块（BusinessBoard）
- 业务大类（BusinessCategory）
- 业务模块（BusinessModule）
- 业务场景（BusinessScene）

原子规则会被分类到一个或多个业务模块，并进一步通过场景规则形成场景挂接。

### 6.2 分类输出字段

分类后会新增或维护以下字段：

| 字段 | 含义 |
| --- | --- |
| `business_taxonomy_label_codes` | 命中的业务分类代码 |
| `business_taxonomy_label_paths` | 命中的业务分类路径 |
| `business_classification_reason` | 分类理由 |
| `business_modules_v2` | 模块名称 |
| `business_categories_v2` | 业务大类 |
| `related_scenarios` | 相关业务场景 |

无法准确分类时使用：

```text
UNCAT-00-00
```

### 6.3 场景挂接与主体侧关系

系统会根据业务分类体系中的场景关键词、原子文本、主体字段等信息生成：

- 场景精召回关系
- 主体词关系
- 场景下高频主体

这一步的目的不是只做分类展示，而是为后续召回提供更小、更准的候选集合。

### 6.4 Neo4j 图谱结构

导入 Neo4j 后，核心节点和边包括：

| 图谱对象 | 含义 |
| --- | --- |
| `BusinessBoard` | 业务板块 |
| `BusinessCategory` | 业务大类 |
| `BusinessModule` | 业务模块 |
| `BusinessScene` | 业务场景 |
| `BusinessAtom` | 法规原子 |
| `BusinessActor` | 场景主体 |
| `TAGGED_AS` | 原子挂到业务模块 |
| `MATCHES_SCENE` | 原子命中业务场景 |
| `SCENE_HAS_ACTOR` | 场景主体关系 |

页面中的“图谱浏览”用于检查：

- 模块宽召回样本
- 场景精召回样本
- 主体细筛效果
- 图结构是否完整

## 7. 人工核查清单

核心文件：

- `src/business_taxonomy_app.py`

人工核查清单的定位是：自动状态只做提醒，不替代人工判断。

### 7.1 核查流程

抽取与构建完成后，人工核查流程如下：

1. 系统读取最新的 Phase1/2、原子抽取、业务分类产物。
2. 按配置比例抽取典型样本。
3. 将 `is_ambiguous=true` 的模糊原子单独抽入“模糊判定”。
4. 人工逐条判断样本为 `通过`、`存疑`、`明显错误` 或 `待判断`。
5. 页面实时统计复核样本数、已判定数、复核完成率和人工通过复核率。
6. 可导出 `sample_review_checklist_*.xlsx` 作为复核留痕。

### 7.2 抽样配置

当前默认配置：

| 配置项 | 默认值 | 含义 |
| --- | --- | --- |
| 典型样本比例 | 10% | 对 Phase1/2、原子抽取、业务分类进行典型样本抽检 |
| 典型样本上限 | 24 | 单表最多抽取典型样本数 |
| 模糊复核比例 | 100% | 模糊原子默认全部进入复核 |
| 模糊复核上限 | 120 | 模糊原子单表复核上限 |

### 7.3 样本组

当前人工判定区包括：

| 样本组 | 目的 |
| --- | --- |
| Phase1/2 判定 | 判断实体抽取方向是否正确 |
| 原子抽取判定 | 判断 who / what / how 和拆分粒度是否可执行 |
| 业务分类判定 | 判断 label path 与分类理由是否贴合原文 |
| 模糊判定 | 判断模糊标签是否合理，是否需要补参数、拆分或回源重抽 |

### 7.4 复核率口径

复核完成率：

```text
已判定样本数 / 总复核样本数
```

人工通过复核率：

```text
通过样本数 / 已判定样本数
```

注意：

- `待判断` 不计入人工通过复核率分母。
- `存疑` 和 `明显错误` 会计入问题样本。
- 模糊原子如果集中出现同类问题，应优先回查 Stage3 提示词或原文切块策略。

## 8. 闭环召回与合规查验

核心文件：

- `src/compliance_recall_controller.py`
- `src/formal_rule_engine.py`
- `src/formal_scene_catalog.py`
- `src/formal_final_judgement_catalog.py`

### 8.1 输入

闭环召回输入包括：

| 输入 | 含义 |
| --- | --- |
| `question` | 合规问题或业务审核问题 |
| `query` | 用于业务定位和召回的短查询 |
| `who` | 主体关键词 |
| `max_rounds` | 最大推理轮次 |

页面支持单问题、多 query，以及批量问题。

### 8.2 初始召回

初始召回综合以下来源：

1. 场景精召回。
2. 模块宽召回。
3. 问题焦点词语义命中。
4. 主体关键词命中。

初始召回的目标是给模型提供第一版证据集合，而不是直接输出最终结论。

### 8.3 集合级判断

模型或符号规则会判断当前证据集合是否足够：

- 是否还能直接生成最终合规结论。
- 证据是否覆盖主体、条件、材料、流程、时限、例外、禁止。
- 是否需要继续召回。
- 如果需要继续召回，应沿哪些方向补证据。

### 8.4 Atom 级最小可执行颗粒度检查

仅召回到抽象条款是不够的。系统会对关键 atom 做颗粒度检查：

- 是否明确办理主体。
- 是否明确提交材料。
- 是否明确审核动作。
- 是否明确时限或金额阈值。
- 是否明确禁止或例外边界。
- 是否存在需要事实核验的条件。

如果 atom 粒度不足，系统会触发补召回或人工复核。

### 8.5 A-F 六类扩召回方向

| 方向 | 名称 | 作用 |
| --- | --- | --- |
| A | 业务向下召回 | 沿当前业务模块向更细场景或子规则下钻 |
| B | 同层横向召回 | 补充同模块、同场景的相邻规则 |
| C | 法规结构邻接召回 | 按条文前后、同章同节、引用关系补证据 |
| D | 规则语义补全召回 | 根据缺口词补材料、流程、阈值、定义等语义证据 |
| E | 例外禁止优先召回 | 优先补充不得、除外、限制、但书类规则 |
| F | 上下位规范补充召回 | 补充上位法、下位规章或关联规范依据 |

### 8.6 停止条件

闭环召回会在以下条件之一停止：

| 停止原因 | 含义 |
| --- | --- |
| `llm_stop` | 模型判断证据已足够 |
| `no_new_candidates` | 已无新增候选规则 |
| `max_rounds` | 达到最大轮次 |
| `llm_connection_error` | LLM 调用失败，回退本地结果 |
| `dry_run` | 只执行本地召回，不调用 LLM |

### 8.7 最终结论类型

当前最终合规结论候选包括：

- `可办理`
- `不可办理`
- `有条件可办理`
- `需补材料后办理`
- `需人工复核`
- `证据不足待补召回`

结论生成必须保留关键依据、缺口、风险提示和下一步建议。

## 9. 多输入并行召回与推理

当前页面已支持两类多输入。

### 9.1 单问题多 query

在“模型推理演示”中，`业务 query` 可以多行输入。

格式：

```text
银行汇票
商业汇票 | 持票人
银行本票<TAB>出票银行
```

含义：

- 每行一个 query。
- 如果写成 `query | who`，该行使用独立主体关键词。
- 如果未写行内 who，则使用页面中的默认主体关键词。
- 多行 query 会并行执行召回与推理，并按 query 展示独立报告。

### 9.2 批量问题

批量问题输入格式：

```text
问题
问题 | query | who
问题<TAB>query<TAB>who
```

如果行内未填写 query 或 who，则使用批量区默认值。

### 9.3 并行数

当前默认并行数：

```text
3
```

当前最大并行数：

```text
8
```

并行执行用于提升多 query 或多问题的召回推理效率。若遇到模型接口限流、超时或连接不稳定，应降低并行数。

## 10. 页面操作流程

主页面：

```powershell
python -m streamlit run ".\src\business_taxonomy_app.py"
```

推荐操作顺序：

1. 在 `抽取与构建` 页配置 API、模型、输入文档和输出文件名。
2. 运行 `Phase1/2`。
3. 运行 `原子抽取`。
4. 运行 `业务分类`。
5. 导入 Neo4j。
6. 到 `人工核查清单` 查看典型样本、模糊样本和通过复核率。
7. 到 `分类概览` 和 `图谱浏览` 检查分类覆盖、场景挂接和召回样本。
8. 到 `模型推理演示` 执行单问题、多 query 或批量问题查验。

默认输出文件名建议保持：

- `phase1_entities_checkpoint.xlsx`
- `legal_atoms_v4_final.xlsx`
- `legal_atoms_business_taxonomy.xlsx`

这样模型推理演示页可以直接读取默认分类结果。

## 14. 风险与处理原则

| 风险 | 表现 | 处理原则 |
| --- | --- | --- |
| 原文切块过粗 | 一个 atom 包含多个规则 | 回查切块和 Stage3 逻辑裂变提示词 |
| 模糊原子过多 | `is_ambiguous=true` 比例异常高 | 优先人工抽查并调整提示词 |
| 分类覆盖不足 | 大量 `UNCAT-00-00` | 补业务分类体系、补关键词或重跑分类 |
| 场景挂接不足 | 场景精召回样本过少 | 检查场景 profile、主体词和原子字段 |
| LLM 连接不稳定 | `LLM_ERROR` | 降低并行数，检查 API Key、Base URL、网络和 VPN |
| 结论过早确定 | 关键禁止或例外未召回 | 强化 E 类例外禁止优先召回 |
| 事实核验缺口 | 法规则充分但事实不明确 | 输出需人工复核或需业务系统补事实 |

## 15. 完成标准

一个法规批次可以认为完成“原子化拆解与构建”，至少应满足：

1. 原子表已生成，且关键字段不为空。
2. 模糊原子已进入人工复核队列。
3. 人工核查清单已完成典型样本判定。
4. 人工通过复核率达到项目可接受阈值。
5. 业务分类覆盖率可接受，未分类样本原因明确。
6. Neo4j 中业务板块、分类、模块、场景和原子节点均可读取。
7. 图谱浏览页能看到模块宽召回和场景精召回样本。
8. 模型推理演示页能基于默认分类文件执行召回和合规判断。
9. 对证据不足、模糊条款、事实核验缺口能明确输出人工复核或补召回建议。

## 16. 当前阶段结论

当前项目已经从“法规文本抽取”推进到“可复核、可召回、可解释的合规查验闭环”阶段。

后续重点不再是单纯提高抽取数量，而是：

- 稳定原子粒度。
- 提升业务分类覆盖率。
- 固化人工核查口径。
- 用人工通过复核率衡量抽取质量。
- 用多 query 并行召回覆盖复杂业务问题中的多个检索入口。
- 将高频缺口沉淀为符号规则，减少单纯依赖模型自由判断。

```text
{
  "atoms": [
    {
      "temp_id": "1",
      "rule_type": "OBL_MANDATORY",
      "behavior_struct": { "who": "...", "when": "...", "where": "...", "what": "...", "how": "..." },
```

当前基础提示词：

```text
## 角色设定
你是一名有丰富经验的银行运营与合规审核专家。
你的任务不是判断某一条知识是否写得完整，
而是判断“当前已召回的知识集合”是否足以支持对一个具体业务问题做出合规判断。

## 任务目标
对于给定的：
1. 业务问题/审核问题
2. 当前召回的知识集合
3. 当前命中的业务层级信息（如业务板块、业务模块、业务场景）
请判断：
当前证据是否已经足够支撑一次可靠的合规判断？
- 如果足够，输出【停止召回】
- 如果不够，输出【继续召回】
并明确指出：
- 缺少的证据类型是什么
- 应该优先往哪个方向扩召
- 为什么不能仅依赖当前业务连接召回结果做结论

## 判断标准
请从以下6个维度逐项判断，只要任意一个维度明显不足，就应继续召回。

### 1. 适用对象是否闭合
当前召回的知识，是否已经明确覆盖了该业务问题对应的主体、客体、票据/账户/产品类型、适用范围？
如果仍无法确认“这条规则是否适用于当前业务对象”，则继续召回。

### 2. 判断条件是否闭合
当前召回的知识，是否已经给出了能够触发判断所需的前提条件、时间条件、金额条件、材料条件、流程条件？
如果缺少前提条件或适用条件，则继续召回。

### 3. 例外与禁止是否闭合
当前召回的知识中，是否已经包含与该问题相关的例外条款、禁止性条款、排除情形、特殊处理规则？
如果只召回到一般规则，而未覆盖例外/禁止，则继续召回。

### 4. 审核动作是否闭合
一线审核人员是否已经知道具体应核查哪些材料、比对哪些字段、确认哪些关系，进而形成结论？
如果仍不知道“看什么、比什么、据什么判”，则继续召回。

### 5. 结论边界是否闭合
基于当前召回结果，是否能够形成明确的“可办理 / 不可办理 / 需补件 / 存在风险”结论？
如果只能得出“可能”“大致”“还需进一步确认”的结论，则继续召回。

### 6. 证据冲突是否已消解
当前召回结果中，是否存在看似冲突、层级不同、适用范围不同的规则，而这些冲突尚未被解释？
如果存在冲突但没有足够证据消解，则继续召回。

## 召回方向判定
如果需要继续召回，请不要笼统地说“继续向下召回”，而要从以下方向中选择最优先的1-3项：
- A. 业务向下召回
- B. 同层横向召回
- C. 法规结构邻接召回
- D. 规则语义补全召回
- E. 例外/禁止优先召回
- F. 上下位规范补充召回

## 输出要求
严格输出 JSON，不要输出额外解释：
{
```

## 18. Prompt 优化优先级

建议按以下顺序优化：

1. 先优化 Stage3，因为它直接决定原子粒度、模糊标签和后续复核压力。
2. 再优化业务分类 prompt，因为分类质量直接影响召回入口。
3. 再优化集合级召回判断 prompt，因为它决定继续召回还是停止。
4. 最后优化最终结论 prompt，保持其克制、稳定、短输出。

不建议优先优化：

- Stage1：当前只是类型扫描，成本和风险较低。
- 映射表辅助 prompt：不在主闭环链路中。

Prompt 版本化建议：

- 将每个 prompt 单独维护为可读文件。
- 每次变更记录：修改原因、影响字段、验证 case、回退版本。
- 对 Stage3 的模糊判断增加本地规则扫描，减少完全依赖模型自由判断。
